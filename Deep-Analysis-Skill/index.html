Section 1

Problem & Opportunity

Problem Statement

Feature owners want a more complete analysis of their experiment, run against a scorecard they choose. Today, getting that analysis means reading the xCard (the experiment scorecard) yourself. Few people at Microsoft know how to read an xCard well. People who don't have to spend time learning before they can reach a conclusion about their experiment.

This affects two groups. The first is feature crews who own experiments. The second is anyone who needs to understand an experiment's result but doesn't know how to read an xCard.

Opportunity

A "Give me a deep analysis" skill that's generally available as the experiment-analyzer plugin removes the need to learn xCards first. Anyone at Microsoft can install it from the DPG-AI-Skilling plugin marketplace into GitHub Copilot CLI or Claude Code, or through Agency. The user supplies the xCard link, the scorecard ID, and the experiment hypothesis, and can optionally list the metrics they expect to be stat-sig. The skill then produces an HTML analysis with sections, tradeoffs to discuss, and a verdict.

PM estimate of time saved: today a deep analysis takes about 3 hours of manual work. The goal is for the skill to finish in about 5 minutes or less.

Evidence

  • PM observation: Reading an xCard is still a niche skill at Microsoft. Feature crews, and people who don't know how to read an xCard, both need a fuller analysis of their experiments.
  • Time-to-analysis: About 3 hours manually versus a target of 5 minutes or less. This is a PM estimate, not a measured baseline.
  • User research, telemetry, support data: TBD No quantitative evidence has been gathered for this spec yet.

Goals & Success Metrics

Goals

  1. Get a deep analysis of a specific experiment and scorecard in about 5 minutes or less, down from about 3 hours of manual work (PM estimate).
  2. Give people who can't read an xCard an analysis they can act on, with sections, tradeoffs to discuss, and a verdict. They shouldn't have to learn xCards first.
  3. Make the skill generally available to anyone at Microsoft through the GitHub plugin marketplace (GitHub Copilot CLI and Claude Code) and through Agency, with one documented way to install it for each.

Section 3

User Scenarios

Scenario 1: Feature crew experiment owner using GitHub Copilot CLI or Claude Code (primary)

A feature owner wants more than the headline results: a fuller analysis tied to the hypothesis they actually set out to test. In GitHub Copilot CLI they add the DPG-AI-Skilling marketplace and install experiment-analyzer, which only needs to be done once. Then they run /experiment-analyzer, or just ask the agent to analyze an ExP scorecard. They provide the xCard link, the scorecard ID, their hypothesis, and the metrics they expect to be stat-sig. The skill writes a standalone HTML report to their workspace with sections, tradeoffs to discuss with their crew, and a verdict.

Scenario 2: Agency user who doesn't know how to read an xCard

A stakeholder needs to understand an experiment's result but has never learned to read an xCard. They already use Agency, so they install the plugin through Agency and start a session. They fill in the three required inputs and skip the metrics list. The skill applies the default metrics for the scorecard's metric set (source: SKILL.md, Required Inputs). They get the same HTML report and verdict and never have to read the xCard themselves.

Edge case: No metrics supplied

The user leaves the optional metrics list empty. The skill reads the scorecard's metric set from Metadata and uses that profile's defaults (source: SKILL.md). This is TC-2.

Edge case: Scorecard on a metric set with no documented profile

Required: the skill analyzes any metric set the user has access to (source: PM). Gap: v1.0.0 lists three supported MetricSets. For any other set, it stops and reports Unsupported metric set: <exact value> (source: metric-set-profiles.md). Until the gap is closed, users with scorecards on other metric sets won't get an analysis.

Edge case: Missing input or prerequisite

The skill asks only for required values it can't parse from the scorecard link or the conversation (source: plugin README, Usage). If a prerequisite is missing (ExP scorecard MCP access, Python 3, or PowerShell 7), the user should get a clear message saying what to install or request. TBD: whether the plugin does this today.

Section 5

Design Direction

UX Flow

Install once: GitHub plugin marketplace (/plugin marketplace add + /plugin install) or Agency
→ Invoke /experiment-analyzer or ask the agent to "analyze ExP scorecard …"
→ Provide xCard link*, scorecard ID*, hypothesis*, and optional expected stat-sig metrics (the agent asks only for what's missing)
→ Skill: scorecard context → statistics → data → hypothesis and decision
→ Standalone HTML decision brief + supporting artifacts written to the workspace · Target: about 5 min or less end to end

The four-step workflow comes from SKILL.md ("Four-Layer Workflow").

Output: HTML Decision Brief

The verdict is one of these recommendations (source: SKILL.md, Hypothesis And Decision):

ShipGradual rampIterate and re-testDo not shipInvalid / Re-runNot tested

Report sections, in order (source: SKILL.md, HTML Deliverable):

  1. A masthead that leads with the decision: recommendation, exact scorecard title, hypothesis, variant IDs, analysis dates, and checkpoint
  2. A KPI strip showing only the outcomes that drive the decision
  3. An executive action sentence, with ramp stages and stop conditions
  4. Setup and validity
  5. Metric performance, covering every declared outcome, guardrail, and durability metric
  6. A metric-definition glossary
  7. Weekday-aware drift and audience consistency
  8. The latest Expedite scorecard update and the next tests to run
  9. A 13-question prompt library with precomputed answers. This includes the tradeoff questions "Are the gains worth the guardrail regressions?" and "Are any audiences helped or harmed differently?"
  10. A provenance footer

Key Interaction Notes

  • The skill runs entirely inside the user's agent CLI. There's no Expedite UI surface.
  • The agent collects inputs conversationally and asks only for what it can't parse from the link or the conversation.
  • The report is written for Technical PMs and SLT first. Technical evidence stays in closed disclosures so data scientists can audit it (source: SKILL.md).

Edge Cases & Empty States

  • Metric set with no documented profile: Required behavior is a full analysis (R-04). v1.0.0 currently stops with Unsupported metric set: <value>, which is the gap tracked in Q3.
  • Assignment imbalance (SRM) on the randomization unit: The decision is Invalid / Re-run and no causal inference is drawn (source: SKILL.md, Hard gates).
  • No matching Expedite record: The report says "Exact Expedite record not resolved" or "Not indexed" and lists the lookup terms it tried (source: SKILL.md).
  • Runtime goes past the target: What the user sees past about 5 minutes is TBD.

Accessibility

  • The report uses native <details> disclosures, which work with a keyboard and screen readers without JavaScript (source: SKILL.md).
  • Status color is never the only signal. A "Reliable improvement" badge always has a visible text label (source: SKILL.md).
  • The report uses semantic headings for each section so screen reader users can navigate it.
Section 6

Open Questions & Risks

Resolved Questions

Plugin address and contract (was Q1, Q2)

The skill is the experiment-analyzer plugin in the experiences-and-devices/DPG-AI-Skilling marketplace. It isn't an HTTP endpoint called through Expedite.

Default metrics (was Q3)

The defaults are profile-specific and chosen from the scorecard's Metadata MetricSet (source: SKILL.md).

Scorecard ID versus link (was Q5)

The ID is read from scorecardIds= when it's present. Otherwise the agent asks for it.

Turning plain-language metric expectations into metrics (was Q6)

The skill turns the hypothesis into a signed metric map and resolves each metric through Metadata and MDL before it looks at any results (source: SKILL.md).

Where output appears (was Q7, Q8)

There's no form and no browser tab. Inputs are collected in the conversation, and the report is written to the user's workspace.

Who can access the marketplace (was part of Q2)

Anyone at Microsoft has access to the marketplace repo and can install the plugin (source: PM). This is now a requirement in R-01.

Open Questions

Q1: What is the confirmed Agency install command?

The Agency-managed commands in Section 4 follow Agency's documented market: spec format but haven't been tested with this plugin. The native /plugin commands should also work inside agency copilot and agency claude. Owner: David Lydston (PM).

Q2: How do users get ExP scorecard access?

Anyone at Microsoft can install the plugin (R-01). To run an analysis, they also need authenticated access to the ExP scorecard MCP endpoint, and the skill can only analyze metric sets the user can access (R-04). How do users get that access, and what does the skill tell them when they don't have it? Owner: TBD.

Q3: How and when will the plugin close the metric-set gap?

R-04 requires every metric set the user can access (source: PM). v1.0.0 documents three MetricSets: IDEAsCommercialCopilotApp, IDEAsCommercialCopilotAppFast, and CommercialAgentEngagementFast. It reports Unsupported metric set for any other. For metric sets without a profile, where will the default metrics, guardrails, and correction families come from? And until the gap is closed, are both test case scorecards on one of the three documented sets? Owner: Ruby Mazumdar (DS).

Q4: What are the reference outputs for the two test cases?

These are needed to verify R-07. Owner: David Lydston (PM).

Q5: How will adoption be measured?

We don't yet know where install and invocation counts would come from for the marketplace and for Agency. Targets are also TBD. Owner: David Lydston (PM).

Q6: Can the full workflow finish in about 5 minutes?

The skill runs four workflow layers and writes a report, a DOCX, and a reproducibility bundle. Runtime hasn't been measured against the 5-minute target. Owner: Ruby Mazumdar (DS).

Risks

Risk 1: Setup is too much for people who don't read xCards

Likelihood / Impact: TBD. The plugin needs an agent CLI, ExP scorecard MCP authentication, Python 3, and PowerShell 7. That's a lot to ask of one of the two target audiences. Proposed mitigations: (1) a one-page setup guide; (2) prerequisite checks with clear messages (R-08); (3) try installation with first-time users.

Risk 2: The published plugin doesn't yet meet the metric-set requirement

Likelihood / Impact: TBD. R-04 requires every metric set the user can access, but v1.0.0 fails closed outside three documented MetricSets. Users on other metric sets would install the plugin and get no analysis. Proposed mitigations: (1) close the gap before GA; (2) add an acceptance test with a scorecard outside the three documented sets; (3) until the gap is closed, state the supported sets in the README and in the skill's response.

Risk 3: Readers can't check the verdict for themselves

Likelihood / Impact: TBD. People who don't read xCards may take the verdict at face value. Existing mitigations in the plugin: technical evidence in disclosures, a provenance footer, and an offline reproducibility bundle (source: SKILL.md). Proposed: have DS review the test case outputs before launch.

Risk 4: The skill depends on a single plugin owner

Likelihood / Impact: TBD. The analysis logic and default metrics are owned by one DS skill author. Proposed mitigation: document the support and on-call path for the plugin before GA.
