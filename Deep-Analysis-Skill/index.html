Section 1

Problem & Opportunity

Problem Statement

Feature owners want a more complete analysis of their experiment, run against a scorecard they choose. Today, getting that analysis means reading the xCard (the experiment scorecard) yourself. Few people at Microsoft know how to read an xCard well. People who don't have to spend time learning before they can reach a conclusion about their experiment.

This affects two groups. The first is feature crews who own experiments. The second is anyone who needs to understand an experiment's result but doesn't know how to read an xCard.

Opportunity

A single "Give me a deep analysis" skill in the fabric-expedite-mcp-app MCP server, launched from the Expedite experiment summary page, removes the need to learn xCards first. The user supplies the xCard link, the scorecard ID, and the experiment hypothesis. They can optionally list the metrics they expect to be stat-sig. The skill calls an analysis plugin written by the Data Science skill owner and returns an HTML analysis with sections, tradeoffs to discuss, and a verdict.

PM estimate of time saved: today a deep analysis takes about 3 hours of manual work. The goal is for the skill to finish in about 5 minutes or less.

Evidence

  • PM observation: Reading an xCard is still a niche skill at Microsoft. Feature crews, and people who don't know how to read an xCard, both need a fuller analysis of their experiments.
  • Time-to-analysis: About 3 hours manually versus a target of 5 minutes or less. This is a PM estimate, not a measured baseline.
  • User research, telemetry, support data: TBD No quantitative evidence has been gathered for this spec yet.

Goals & Success Metrics

Goals

  1. Get a deep analysis of a specific experiment and scorecard in about 5 minutes or less, down from about 3 hours of manual work (PM estimate).
  2. Give people who can't read an xCard an analysis they can act on, with sections, tradeoffs to discuss, and a verdict. They shouldn't have to learn xCards first.
  3. Make the Data Science deep-analysis plugin available as a skill in fabric-expedite-mcp-app, launched from the Expedite experiment summary page.

Section 3

User Scenarios

Scenario 1: Feature crew experiment owner (primary)

A feature owner is on the Expedite experiment summary page for their experiment. They want more than the headline results: a fuller analysis tied to the hypothesis they actually set out to test. Under Suggested actions to explore this experiment, they click "Give me a deep analysis on this." They paste in the xCard link and the scorecard ID, enter their hypothesis, and list the metrics they expect to be stat-sig. They submit, and a new browser tab opens with an HTML analysis: sections, tradeoffs to discuss with their crew, and a verdict.

Scenario 2: Someone who doesn't know how to read an xCard

A stakeholder needs to understand an experiment's result but has never learned to read an xCard. From the same experiment summary page, they launch the skill and fill in the three required inputs. They leave the metrics list empty, so the skill uses its default metrics, which the skill author defined. They get the same HTML analysis and verdict and never have to read the xCard themselves.

Edge case: No metrics supplied

The user leaves the optional stat-sig metrics list empty. The skill still runs and uses the default metrics the skill author defined. This is TC-2. TBD: whether the output should say which default metrics were used.

Edge case: Invalid or missing required input

The user leaves a required field empty, or enters a scorecard ID that isn't an integer. The skill doesn't call the plugin. The form marks the field in question and explains what's wrong.

Figma: TBD

Key Interaction Notes

  • The new chip uses the same style as the existing suggested-action chips and appears after them.
  • In V1 the user types in every input. Nothing is pre-filled from the page, even though the page already knows which experiment is open.
  • The optional metrics field takes metric display names. Leaving it empty is a supported path, and the skill author's defaults are used.
  • The result opens in a new browser tab so the user doesn't lose their place on the experiment summary page.

Edge Cases & Empty States

  • Missing or invalid required input: The field in question is marked with an error message and Submit stays disabled.
  • Plugin error: An error message with a Retry button. Exact wording and retry policy are TBD.
  • Runtime exceeds target: Behavior past about 5 minutes (keep waiting, time out, or notify the user when it's done) is TBD.
  • Pop-up blocked: If the browser blocks the new tab, show a link the user can click to open the analysis.

Accessibility

  • The chip, form fields, and Submit button can all be reached with Tab and Shift+Tab. The chip and Submit button activate with Enter or Space.
  • Required fields are marked for screen readers. Validation errors are linked to their fields and announced. The loading state is announced when it starts and when it ends.
  • The HTML analysis uses semantic headings for its sections, the tradeoffs, and the verdict, so screen reader users can navigate it.
Section 6

Open Questions & Risks

Open Questions

Q1: What is the plugin address?

The skill calls a plugin at an address the PM will provide later. Owner: David Lydston (PM).

Q2: What is the plugin contract?

Still unknown: the request format, authentication, response format (an HTML document or a URL to one), expected latency, and timeout. Owner: Ruby Mazumdar (DS).

Q3: Which default metrics are used, and should the output list them?

The skill has defaults that its author knows and defines. Should the analysis, or the input form, show which defaults were used for a run? Owner: Ruby Mazumdar (DS).

Q4: What are the reference outputs for the two test cases?

These are needed to verify R-09. Owner: David Lydston (PM).

Q5: Should the scorecard ID be checked against the xCard link?

Some xCard links include a scorecardIds parameter that matches the scorecard ID input (TC-1). Others don't include one at all (TC-2). Should the skill flag a mismatch when the link does include an ID, or should it just trust the scorecard ID input? Owner: TBD.

Q6: How are metric expectations written in plain language matched to metric display names?

The optional input is a list of metric display names. But experimenters may describe their expectations in plain language, including direction and thresholds, as TC-1 does, rather than giving exact metric display names. Who maps these to scorecard metric names: the user, the skill, or the plugin? And should direction ("increase") be part of the input? Owner: Ruby Mazumdar (DS) and David Lydston (PM).

Q7: Form or chat prompt?

V1 has the user type in every input. Should that happen in a structured form, as in Wireframe B, or in a chat prompt? Owner: David Lydston (PM).

Q8: Where is the HTML analysis hosted, and who can see it?

Still unknown: whether the analysis is saved, whether it can be shared by link, how long it's kept, and whether it respects the same permissions as the experiment and scorecard. Owner: TBD.

Q9: What are the adoption and success-rate targets?

Only the time-to-analysis target (about 5 min or less) has been set. Owner: David Lydston (PM).

Risks

Risk 1: Readers can't check the verdict for themselves

Likelihood / Impact: TBD. A main audience is people who don't know how to read an xCard, so they may take the verdict at face value. Proposed mitigations: (1) show the inputs used (including default metrics) at the top of the analysis; (2) link back to the source xCard; (3) have DS review the test case outputs before launch.

Risk 2: Runtime goes past the 5-minute target

Likelihood / Impact: TBD. Plugin latency hasn't been characterized yet. Proposed mitigations: (1) measure runtime on both test cases before launch; (2) show progress while the skill runs; (3) decide what happens on timeout (see Edge Cases).

Risk 3: Metric names typed by the user don't match the scorecard

Likelihood / Impact: TBD. Users typing free-text metric display names may not match the scorecard's metric names exactly (see Q6). Proposed mitigation: the plugin reports any metric names it couldn't match instead of silently dropping them.

Risk 4: The skill depends on a single plugin owner

Likelihood / Impact: TBD. The analysis logic and default metrics are owned by one DS skill author. Proposed mitigation: document the plugin contract, defaults, and on-call and support ownership before GA.
