Section 1

Problem & Opportunity

Problem Statement

Aggregated Session Happiness (ASHA) metrics are the critical guardrails for the Microsoft Copilot App — they tell us whether a shipped feature degraded App Boot, Chat Tried, or Interruptions. But ASHA metrics are inherently high-variance: they are built from session-level user experience signals whose per-user values swing widely for reasons that have nothing to do with the treatment (device class, network conditions, tenant configuration, individual usage habits). The consequence is duration. To detect a movement in ASHA that matters, a flight has to accumulate enough users to overwhelm that natural noise — so flights sit at a given ramp far longer than the product decision needs, and crews wait weeks for a guardrail read that the underlying data could have supported far sooner.

This is the exact problem CUPED (Controlled-experiment Using Pre-Existing Data) was invented to solve, at Microsoft, in 2013. The ExP platform already supports CUPED-based variance reduction as a metric-authoring configuration. IDEAS scorecards do not use it. Variance reduction is a per-scorecard configuration change, and no one has made that change for the ASHA scorecard — so every ASHA flight pays the full duration cost of unreduced variance even though the pre-experiment data needed to remove much of it already exists in our pipelines.

Opportunity

Configuring CUPED variance reduction on the ASHA scorecard converts existing, already-collected pre-period data into experiment velocity:

  • Shorter flights at the same confidence. Variance reduction lowers the standard error of the treatment effect without touching the point estimate. The same decision quality arrives with less accumulated exposure — published implementations report meaningful reductions in required sample size when the covariate is well correlated with the outcome.
  • Guardrails that keep pace with the product. If ASHA can be read sooner, guardrail evaluation stops being the long pole that holds a ramp at 5% or 20% while the feature crew waits.
  • More real regressions caught. Higher sensitivity at a fixed flight duration means genuine ASHA degradations that previously sat below the detection threshold now surface — the guardrail actually guards.
  • A repeatable pattern. ASHA is the pilot. Once the covariate selection, validation, and communication playbook exists, the same per-scorecard configuration can be extended to other IDEAS scorecards with high-variance metrics.
  • Zero new data collection. The covariate for ASHA is, in the standard formulation, the same ASHA metric measured over a pre-experiment window — data we already produce.

Evidence

  • Method provenance. CUPED was created by Microsoft in 2013 (Deng, Xu, Kohavi, Walker — Improving the Sensitivity of Online Controlled Experiments by Utilizing Pre-Experiment Data) and has since been adopted as industry standard at Netflix, Booking.com, and the BBC. It is not experimental — it is mature, well-understood, and already supported by our platform.
  • Platform support already exists. ExP documents variance reduction as a metric-authoring configuration (Configure Variance Reduction) and publishes an explainer at aka.ms/exp/cupedvr. This spec is a configuration and validation effort, not a platform build.
  • The math is well characterised. The CUPED-adjusted metric is Ŷi = Yi − θ(Xi − X̄) with θ = cov(X,Y) / var(X), and the resulting variance is var(Y) × (1 − corr(X,Y)²). Variance reduction is therefore entirely a function of how well the pre-period covariate correlates with the in-experiment outcome — which makes covariate selection the single highest-leverage design decision in this spec.
  • ASHA is live and owned. ADO Deliverable #7219414 — ASHA Metrics for MCA on scorecard (Area: IDEAs\Growth\Experimentation\Scorecard) established the ASHA metric set on IDEAS scorecards, tracking the App Boot, Chat Tried, and Interruptions pillars for MCA Win32, commercial first. Related delivery work continues under #7456513 — Create ASHA scorecards. The scorecard exists; the variance reduction configuration is the gap.
  • Guidance on window length. The original Microsoft work found the optimal pre-experiment window is typically 1–2 weeks — shorter windows do not capture enough variance, longer windows introduce noise — with longer windows needed for longer experiments so the same users are observed in both periods.
  • Prior internal precedent. CUPED methodology was previously explored inside Microsoft for NPS impact variance reduction (ADO #3036909, #3036917), confirming both familiarity with the technique and the pattern of evaluating candidate covariates empirically before adoption.
Section 2

Goals & Success Metrics

Goals

  1. Reduce the flight duration required to reach a confident ASHA guardrail read, by configuring CUPED variance reduction on the ASHA scorecard using ExP's existing metric-authoring capability
  2. Select and empirically validate the pre-experiment covariate for each ASHA pillar metric (App Boot, Chat Tried, Interruptions), documenting the measured correlation and the realised variance reduction for each
  3. Prove unbiasedness before rollout — demonstrate on historical flights and A/A tests that CUPED-adjusted point estimates match unadjusted estimates while confidence intervals narrow
  4. Make the change legible to feature crews: it must be obvious on the scorecard which metrics are variance-reduced, by how much, and what that means for interpreting the result
  5. Produce a reusable playbook so extending variance reduction to the next IDEAS scorecard is a configuration exercise, not a research project

Success Metrics

Primary Metric
Time-to-Confident ASHA Read
Target: ≥30% reduction in median days-to-statistical-significance for ASHA pillar metrics on flights with a true effect · Baseline: measured on the trailing 2 quarters of ASHA flights before rollout
Primary Metric
Realised Variance Reduction
Target: ≥20% variance reduction on at least 2 of the 3 ASHA pillar metrics · Measured as 1 − (adjusted variance / unadjusted variance) on production flights
Secondary Metric
Covariate Coverage
Target: ≥80% of users in a typical MCA flight have usable pre-experiment covariate data · Users without pre-period data fall back to the unadjusted metric
Secondary Metric
Regression Detection Rate
Target: measurable increase in the share of flights where an ASHA guardrail movement is flagged stat-sig at a fixed exposure level, without an increase in false positives
Guardrail Metric
Point-Estimate Stability (Unbiasedness)
Must maintain: CUPED-adjusted treatment effect matches the unadjusted effect within a documented tolerance across the historical backtest — CUPED must narrow intervals, never shift conclusions
Guardrail Metric
A/A False-Positive Rate
Must maintain: false-positive rate on A/A tests with CUPED applied stays at or below the nominal α (no inflation from the adjustment)
Guardrail Metric
Scorecard Compute & Freshness
Must maintain: ASHA scorecard generation latency and freshness SLA (≤24 hours) unchanged after the pre-period join is introduced

Explicit Non-Goals

Building a variance reduction engine — ExP already provides CUPED; this is metric authoring and configuration
Applying variance reduction to every IDEAS scorecard in V1 — ASHA is the pilot, expansion is a follow-on
Non-linear or ML-based variance reduction (CUPAC, multi-covariate regression adjustment) — V1 uses standard single-covariate linear CUPED
Changing ASHA metric definitions, pillars, or thresholds — the metric semantics are consumed as-is
Changing the decision framework or shipping criteria — Expedite verdict logic is unchanged; only the precision of the inputs improves
Retroactively restating historical scorecards with CUPED-adjusted values — applies going forward
Variance reduction for flights with no pre-experiment period (brand-new-user cohorts) — those fall back to unadjusted metrics
Section 3

User Scenarios

Scenario 1 — "Feature Crew Ramping Faster" (Primary)

Sam owns a Copilot App feature and is ramping a flight from 5% to 20%. The gate is ASHA: leadership will not approve the ramp until the guardrails read clean. Today, Sam waits roughly three weeks for the ASHA confidence intervals to tighten enough to say anything. With CUPED configured on the ASHA scorecard, the same flight reaches a confident read in noticeably less time, because the pre-period ASHA values for those same users have absorbed a large share of the natural user-to-user variation. Sam sees the tighter interval on the scorecard, notes the "Variance reduced (CUPED)" chip on the App Boot metric, and takes the ramp decision materially earlier.

Scenario 2 — "Data Scientist Validating the Adjustment"

Dana is an IDEAS Data Scientist responsible for signing off on the change. Before rollout she runs the backtest harness across the trailing two quarters of MCA flights, comparing adjusted and unadjusted results side-by-side for each ASHA pillar. She confirms the point estimates line up within tolerance, the intervals narrow, and the A/A false-positive rate is unchanged. She records the measured correlation between the pre-period covariate and the in-experiment outcome for each pillar — App Boot correlates strongly, Interruptions less so — and this evidence determines which pillars get CUPED enabled at launch.

Scenario 3 — "Growth Leader Reading a Guardrail"

Jordan reviews the ASHA guardrails across the Copilot Growth portfolio. On the scorecard, variance-reduced metrics carry a visible indicator and a hover explaining "This metric uses CUPED variance reduction with a 14-day pre-experiment covariate; observed variance reduction 34%." Jordan does not need to understand the estimator — only that the number is more precise and that the adjustment does not change what the effect is, only how tightly it is bounded. Crucially, Jordan can see that a regression flagged this week would previously have taken another ten days to surface.

Edge Case — New Users With No Pre-Experiment Data

A flight targets newly-installed MCA users, most of whom have no pre-experiment window. The scorecard applies the standard fallback: users without covariate data use the unadjusted metric, and the scorecard surfaces a coverage chip ("CUPED coverage: 31% of users — limited variance reduction on this flight"). Where coverage falls below a configured floor, the metric renders unadjusted with an explicit note rather than advertising a reduction it did not achieve.

Edge Case — Covariate Contaminated by Treatment

A flight's assignment predates the nominal pre-period boundary, or a prior overlapping flight has already shifted the covariate for one arm. CUPED is only valid when the covariate is untouched by the treatment. The validation check compares covariate means across arms; if they differ beyond tolerance, the scorecard suppresses the adjustment for that flight and raises a data-quality warning rather than reporting a biased result.

Edge Case — Numbers Change Mid-Flight

Rollout lands while flights are in-flight, and a crew notices their ASHA confidence interval narrowed overnight without the underlying data changing. The scorecard carries a dated changelog banner on affected metrics ("CUPED variance reduction enabled on 2026-11-03 — intervals narrowed; point estimates unchanged") with a link to methodology, so the change is explained at the point of confusion rather than in a mail thread.

Section 5

Design Direction

How the Adjustment Works

1. Pick the covariate (X) — for each ASHA pillar, the same pillar metric measured over a 1–2 week pre-experiment window. Must be strongly correlated with the in-experiment outcome and untouched by the treatment.

2. Estimate θ — θ = cov(X,Y) / var(X), fit on the pooled sample across arms (never per-arm, which reintroduces bias).

3. Adjust each unit — Ŷi = Yi − θ(Xi − X̄). Centering on the covariate mean preserves unbiasedness.

4. Variance falls — var(Ŷ) = var(Y) × (1 − corr(X,Y)²). A covariate correlating at 0.6 removes ~36% of the variance; at 0.8, ~64%.

5. Same test, tighter interval — the test runs on the adjusted metric and variance. The point estimate is unchanged; the confidence interval narrows.

Where It Shows Up on the Scorecard

  • Metric row indicator: a compact "VR" / "CUPED" chip next to any variance-reduced ASHA metric, consistent with existing scorecard chip styling
  • Detail on hover / expand: covariate used, pre-period window length, measured correlation, realised variance reduction (%), and covariate coverage (%)
  • Coverage warning: where covariate coverage is below the configured floor, the chip switches to a muted state and the detail explains that the metric is reported unadjusted
  • Balance warning: where the covariate balance check fails, the adjustment is suppressed and a data-quality warning renders on the metric
  • Rollout changelog banner: dated, dismissible, on affected metrics for a defined window post-launch
  • Methodology link: every indicator links to a single canonical methodology page explaining CUPED in plain language for non-statisticians

Rollout Sequencing

  • Phase 0 — Feasibility: covariate availability and coverage confirmed in the ASHA / MetricFeed pipeline (R-01, R-02)
  • Phase 1 — Validation: historical backtest and A/A runs; per-pillar go / no-go based on measured correlation and variance reduction (R-05, R-06)
  • Phase 2 — Shadow: adjusted values computed alongside unadjusted, visible to IDEAS DS only, for a defined period on live flights
  • Phase 3 — GA: variance reduction enabled on qualifying ASHA pillars with the changelog banner, indicators, and methodology page live
  • Phase 4 — Expand: playbook published; candidate next scorecards identified

Positioning Boundary

Variance reduction changes the precision of scorecard inputs, not the decision framework. ExP scorecards and Expedite remain the decision surface; CUPED makes their verdicts available sooner and on firmer statistical footing. Nothing about what constitutes a ship-blocking ASHA regression changes in this spec.

Section 6

Open Questions & Risks

Open Questions

Q1: How strongly does pre-period ASHA correlate with in-experiment ASHA, per pillar?

This is the question that determines whether the whole spec is worth doing, and it must be answered empirically before Phase 3. Variance reduction is exactly 1 − corr² — a covariate correlating at 0.3 buys ~9% and is probably not worth the complexity; at 0.7 it buys ~49% and transforms flight duration. App Boot, Chat Tried, and Interruptions may land in very different places. Owner: IDEAS DS. Blocker for: per-pillar go / no-go.

Q2: Is pre-experiment ASHA data actually available at flight assignment time?

ASHA flows through Nitro v2 into MetricFeed to generate daily user / day / outcome streams. We need to confirm the retained history is deep enough to construct a 1–2 week pre-period for the users in a flight, at the right assignment unit, without building a new pipeline. Owner: Engineering + IDEAS DS.

Q3: What is the right pre-period window, and how does it change for long flights?

Microsoft's original guidance is 1–2 weeks, with longer windows for longer experiments so the same users appear in both periods. MCA flights vary widely in duration. Do we set a single fixed window, or scale it with planned flight duration? Owner: IDEAS DS.

Q4: How much of the MCA flight population is genuinely new (no pre-period)?

CUPED degrades gracefully for users without pre-period data, but if a large share of a typical MCA flight is new users, realised reduction will fall well short of the theoretical maximum. We need the coverage distribution across recent flights before locking the primary metric target. Owner: IDEAS DS.

Q5: Should CUPED be default-on for the ASHA scorecard, or opt-in per flight?

Default-on maximises the duration benefit and keeps interpretation consistent across the portfolio; opt-in gives crews an escape hatch but fragments how results are read. Recommendation is default-on per qualifying pillar, with suppression driven by automated data-quality checks rather than user choice — but this needs confirmation with DS and Growth leadership. Owner: PM + DS.

Q6: Do overlapping flights contaminate the covariate?

If a user was in a prior flight during the pre-period, the covariate may already reflect a treatment effect. On a heavily-flighted surface like MCA this is not hypothetical. Does the balance check (R-07) catch this adequately, or do we need explicit exclusion rules? Owner: IDEAS DS + Flights.

Q7: Which scorecard is next after ASHA?

The playbook is only valuable if it gets used. Candidates should be scored on metric variance, pre-period data availability, and how often duration is the binding constraint on the decision. Owner: PM.

Risks

Risk 1: Correlation is too weak to matter

Likelihood: Medium · Impact: High — if pre-period ASHA correlates weakly with in-experiment ASHA, variance reduction will be marginal and the effort will not move flight duration. Mitigation: Measure correlation first (Q1) as a Phase 0/1 gate before any configuration work; be willing to enable CUPED on only the pillars that clear the bar, and to evaluate alternative covariates (R-16) for the ones that do not.

Risk 2: Loss of trust when scorecard numbers change

Likelihood: High · Impact: Medium — feature crews will notice intervals narrowing and may suspect the data changed, or that results are being massaged toward "ship". Mitigation: Publish the backtest showing point estimates unchanged; ship the changelog banner (R-10), the per-metric indicators (R-09), and a plain-language methodology page before GA, not after; brief the highest-volume crews directly.

Risk 3: Contaminated covariate produces biased results

Likelihood: Medium · Impact: High — CUPED is only valid when the covariate is unaffected by the treatment. Overlapping flights, pre-period leakage, or a mis-specified assignment boundary would silently bias guardrail reads on the metrics leadership trusts most. Mitigation: Automated covariate balance check per flight with suppression (R-07); explicit A/A validation (R-06); shadow phase before GA.

Risk 4: Poor covariate coverage on new-user flights

Likelihood: Medium · Impact: Medium — growth flights frequently target acquisition and onboarding, exactly the population with no pre-period. The advertised benefit would not materialise where crews most want speed. Mitigation: Report coverage per flight (R-08); set expectations explicitly that acquisition flights see limited benefit; investigate alternative covariates (device / tenant-level priors) as a V2 candidate.

Risk 5: Correlation decays over time

Likelihood: Medium · Impact: Low–Medium — as MCA evolves, the relationship between pre-period and in-experiment ASHA may weaken, quietly eroding the benefit while the scorecard still advertises variance reduction. Mitigation: Ongoing monitoring of realised reduction and correlation, with a degradation alert and a named owner (R-11).

Risk 6: Compute cost or freshness regression

Likelihood: Low–Medium · Impact: Medium — joining a pre-period window per user adds work to ASHA scorecard generation and could push against the freshness SLA. Mitigation: Guardrail metric on scorecard latency and freshness; measure during the shadow phase before GA; window length is a tunable lever if cost becomes an issue.

Risk 7: Dependency on ASHA scorecard delivery timeline

Likelihood: Medium · Impact: Medium — ASHA scorecard work is still active (#7219414 In Progress, #7456513 On Track). Configuring variance reduction on a scorecard whose metric set is still settling risks rework. Mitigation: Sequence Phase 0/1 analysis to run in parallel with ASHA scorecard stabilisation; gate configuration (Phase 3) on the pillar metric definitions being locked.
